# TODO / deferred work

Every deferral, approximation, shortcut, or open question found while
implementing goes here. Nothing is dropped silently.

## Where things stand

Every client-side section of MS-PSRP is implemented and tested; see
`SPEC-COVERAGE.md`. The deviations from the specification text were each
researched against the PowerShell sources and against a live server, and the
findings are in the rows below. Three of the five entries turned out to rest on
reasoning that was wrong or unverified, and have been corrected rather than
quietly kept.

What remains genuinely divergent is narrow: accepting protocolversion 2.3 and
above (PSRP-11), and two places where the specification asks for something no
WSMan client can do -- an empty rsp:Command (PSRP-08) and a mustComply OptionSet
on wxf:Connect (PSRP-25). In both of those Microsoft's own client behaves as
this one does, and in both the field is never read by the server.

The entries still open are not missing protocol work. PSRP-28 records a
constraint on any future move to protocol 2.4. PSRP-03 and PSRP-05 exist only to
support a non-Windows port, which would mean replacing the transport and the XML
backend together; neither affects correctness against a Windows server.

## Rules## Rules

- Each entry gets a stable id `PSRP-nn`. Code references it as `/* TODO(PSRP-nn) */`.
- An entry records: what, which spec section, why deferred, and what "done" means.
- Entries are only closed when the behaviour is implemented **and** tested.
- **Before declaring any phase or the project done**, re-read this file top to
  bottom and reconcile it against `SPEC-COVERAGE.md`. Any `deferred` row in the
  coverage file must have a matching open entry here, and vice versa.

| PSRP-08 | Transport | 3.1.5.3.3 | rsp:Command is a single space, not empty | Closed as a spec defect the reference implementation shares. The spec says the Command element MUST be empty, but no WSMan client can obey it: WSManRunShellCommand and its Ex form reject "" and NULL in client-side parameter validation with 0x80338180, sub-millisecond, no handle and no request sent, under every flag and with or without an arg set; any non-empty string passes, including a lone tab. Microsoft's client carries the same workaround verbatim -- WSManTransportManager.CreateAsync passes (_cmdLine == null || _cmdLine.Length == 0) ? " " : ... above the comment "WSManRunsShellCommand doesn't accept empty string" -- and normally diverges further by putting the pipeline's command text (truncated to 255 chars) in the field. The space is inert: it serializes as a literal 0x20 in <rsp:Command> </rsp:Command>, and pwrshplugin never reads the field at all. Not matching PowerShell's command-text behaviour is deliberate: it is ignored by the server and would leak pipeline text into WinRM's logs. | closed |
| PSRP-09 | Host calls | 2.2.6 | Typed decoding of host method parameters (mp) | Closed: the 2.2.6.1 encodings are implemented. What remains undone is mapping each host *method* signature onto typed arguments, which is a job for whatever implements an interactive host, not for the protocol library. | closed |
| PSRP-10 | Metadata | 2.2.3.23 | Full ParameterMetadata detail (type, aliases, switch flag, mandatory) | Closed: each parameter's type name, aliases, switch flag and dynamic flag are read alongside its name, index-aligned with the names array so a caller can walk both together. A parameter whose metadata object is missing still gets an entry carrying its name, so one odd parameter does not cost the caller the rest. There is no Mandatory property in 2.2.3.23; it belongs to the parameter *set* metadata, which the spec does not define a wire type for. | closed |
| PSRP-11 | Negotiation | 3.1.5.4.1.2 | Version table is not enforced literally | Closed, with the original rationale corrected: it was wrong. The check accepts protocolversion major 2 minor >= 1, requires SerializationVersion 1.1.0.1 when present, and ignores PSVersion. Two of those three the spec already permits: its own hedge says that when protocolversion is 2.1 or 2.2 the client SHOULD reach NegotiationSucceeded even if another row mismatches and MAY go Broken, so ignoring PSVersion is licensed and breaking on a foreign SerializationVersion exercises the MAY. Only accepting 2.3+ is a real divergence. The entry previously claimed PowerShell 5.1 announces PSVersion 5.1 and that the strict table would break every modern server. Both are false, and neither was ever measured. RemoteSessionCapability hard-codes new Version(2, 0) for client and server alike; PSVersion is 2.0 on the wire from every PowerShell. And a server echoes the client's protocolversion whenever it is 2.0-2.3, so against our 2.2 offer this server answers 2.2; patching the offer to 2.4 revealed its true ceiling of 2.3. The relaxation is therefore defensive, not load-bearing. Not tightened: a PSVersion check would match MS's client but buy nothing the spec requires, and bounding the minor would only break against a future server. | closed |
| PSRP-12 | Discovery | 3.1.4.10.1 | Enumerating disconnected shells and commands on a server | Closed: implemented via IWSManSession::Enumerate. The earlier note here was wrong. The flat WSMan C API has no enumerate entry point, but the WSMan *automation* interface does, and it is the same one `winrm enumerate` uses. Live-verified: the enumeration lists our own open pool with a matching ShellId. Supplying credentials needs WSManFlagCredUsernamePassword, which the C API infers from the authentication struct and the automation API makes you state. | closed |
| PSRP-13 | Error handling | 3.1.7, 3.1.5.1 r3, 3.1.1.2.2 | Pool goes Broken, not Closed, on a processing error | Closed, and it was never a divergence. 3.1.1.2.2 defines Closed only as the outcome of Closing -> a successful wxf:DeleteResponse; there is no error transition into Closed. "Closed as specified in 3.1.1.2.2" names the closing procedure -- stop pipelines, send wxf:Delete -- and that procedure itself ends in Broken whenever the shutdown is not clean. 3.1.5.3.13 uses the same shape for a fault: Broken plus Delete. PowerShell agrees: RemoteRunspacePoolInternal.HandleSessionClosed sets RunspacePoolState.Broken for any close not initiated from Closing, commented "this close is happening because of data structure handler error"; only a user-initiated close reaches Closed. What was actually missing was the other half of the procedure: notify_fault now fails every pipeline still in the table, as PowerShell does, so a caller waiting on a terminal pipeline event is not stranded. The Delete remains the transport's job (psrp_transport_close_shell / psrp_transport_free), which 3.1.5.1 rule 5 permits after Broken, because the session performs no I/O. | closed |
| PSRP-14 | Transport | -- | WinHTTP holds a connection Event per discarded session for about 60s | Closed, and the original entry was wrong in every particular. It claimed WSMan leaks a process handle per discarded session and that CoUninitialize does not reclaim it. The handles are Event objects created inside webio.dll, WinHTTP's I/O layer, identified by hooking CreateEvent* and attributing live handles to their creating stack: 60 of 62 came from one WinHTTP stack, with no growth in any other object type. The whole three-way signature reproduces in 40 lines of plain WinHTTP with no WSMan, no COM and none of this library's code, so blaming WSMan was misattribution, and the CoUninitialize claim was doubly wrong since COM is not involved. Above all they are not leaked: a scavenger pass at about 60s releases them, to below the count the process started with, and growth is bounded by rate x 60s rather than by session count -- at 6000 iterations the curve bends exactly where the first scavenge falls due and flattens. The original 100, 500 and 1000 iteration runs all finished inside a single scavenge interval, which is why they looked linear; they measured a transient and it was extrapolated into an unbounded leak. An audit for unreleased handles in the library found the normal path clean. psrp_discovery_t and transport reuse stay, as an efficiency measure rather than a workaround for a platform defect. | closed |
| PSRP-15 | Transport | 3.1.5.3.7 | Intermittent failure when cycling transports in a tight loop | Closed: root-caused to a race in the Receive cancellation. Retargeting Receive cancels the in-flight operation, which reports ERROR_OPERATION_ABORTED, and a single expect_abort flag marked that as ours. But cancellation is asynchronous: the completion can arrive after the replacement Receive has been posted and the flag cleared, and the abort is then recorded as a server fault. Replaced with a count of outstanding cancellations that only a consuming callback decrements, and which the receive reset deliberately leaves alone. Reproduced at cycles 41, 48 and 72 before the fix; 400 consecutive cycles clean after it. Guarded by tests/interop/test_stress.c. | closed |

| PSRP-25 | Transport | 3.1.5.3.14 | No OptionSet on wxf:Connect | Closed as a spec defect, with the cause corrected: it is mustComply, not the option and not its spelling. Any option passed to WSManConnectShell with mustComply TRUE stays on the shell handle, is re-sent on the next operation, and the server rejects that Receive with 0x80338039. Measured across 13 live runs: fatal for protocolversion 2.2, for 2.1, for 9.9 and for an invented option name alike, and equally fatal spelled ProtocolVersion as the spec's Connect table spells it, so name and case are irrelevant. mustComply FALSE always works, but that is no longer the option the spec asks for, and the server is not reading it anyway -- protocolversion 9.9 and a bogus option name both pass the Connect unchallenged. mustComply TRUE with optionsMustUnderstand FALSE is rejected on the Connect itself. So no spelling satisfies 3.1.5.3.14 and functions. Microsoft's client does the same: ConnectAsync passes IntPtr.Zero for the Connect option set, only CreateAsync builds one, and server-side WSManPlugin.EnsureOptionsComply is reachable only from the create path. | PSRP-26 | Transport | 3.1.4.10.2 | Reconnect reattached the shell but not its command | Closed: WSManReconnectShell does not reattach commands; output a pipeline produced while disconnected stays buffered against the command until WSManReconnectShellCommand is called, which the transport never did. | PSRP-27 | Session | 3.1.5.3.5 | Outgoing bytes for different pipelines shared one queue | Closed as a latent-correctness fix, not an observed failure. The session held one outgoing buffer and one priority buffer, so a caller running two pipelines at once had both pipelines' input concatenated in take_output with no way to tell which command each belonged to. The bundled WSMan transport runs one command at a time and never hit it, but the sans-IO layer should not force that limitation on a transport that does not share it. Bytes are now queued per destination (pool or pipeline, ordinary or priority stream); take_output still drains everything pool-first for the one-at-a-time case, and take_output_for / next_pending expose the per-destination view a concurrent transport needs. Unit-tested; not driven against a server, because the in-repo transport cannot run two live pipelines to exercise it honestly. | closed |
| PSRP-28 | Negotiation | 2.2.2.1 | Protocol 2.4 deprecates the session key exchange | Not a defect today, a constraint on a future change. RemotingConstants in PowerShell lists 2.4 as PowerShell 7.6 and ProtocolVersionCurrent, and 2.4 makes PUBLIC_KEY, PUBLIC_KEY_REQUEST and ENCRYPTED_SESSION_KEY obsolete when both ends negotiate it. This client announces 2.2, so a server echoes 2.2 and the exchange stays correct. If the announced version is ever raised to 2.4 or above, the key exchange must become conditional on the negotiated version or the two ends will disagree about how a SecureString is protected. Recorded so the coupling is not rediscovered the hard way. | open |
